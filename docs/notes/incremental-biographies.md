# Incremental memoires

Date: 2026-09-06. Story schema 17; profile schema remains 5.

## Behavior

`helper/biography_updates.py` plans reuse, append, or rebuild inside the Python
history preparation workflow. No additional collection or model work runs on
the DF thread. The existing reader displays the saved story during updates.

- Equivalent semantic evidence reuses the story, with no model request.
- A deterministic significance filter defers routine updates without calling the
  model. The reader reports "No significant new developments. Saved memoire
  unchanged." Prepared timeline data remains current; the story revision and
  written-evidence checkpoint do not advance, so deferred changes accumulate.
- Compatible new timeline events / newly occurring indexed episodes can append
  one or two paragraphs. The model receives the entire bounded prior story as
  `prior_narrative`, explicitly marked generated interpretation, plus separate
  verified baseline/event context and the current compact character profile.
- Old prose is joined locally, not regenerated by the model. Validate required
  new factual anchors in the continuation and all current anchors in the combined
  story. Repeated exact paragraphs, empty output, and oversized output fail safely.
- Corrected/enriched references, changed stable character facts, newly discovered
  old events, changed/dropped selected historical episodes, and incompatible
  history trigger a rebuild. This conservative first version does not selectively
  edit old paragraphs. Not every changed profile will qualify for append.
- Missing legacy memory is rebuilt lazily on a requested update; deployment alone
  does not queue every dwarf. Model/contract changes likewise require a new version.
- Stop appending above 5,500 UTF-8 bytes or after four continuations. The next
  changed-evidence update rebuilds from current verified input, keeping the existing
  8,000-byte display limit. Continuations are capped at 2,000 bytes. Unchanged
  stories do not trigger consolidation. Separate archival chapters and rolling
  narrative summaries are deferred; the current bounded story fits in context.

## Significance policy (initial tuning)

These are editorial thresholds, not DF mental-state diagnoses or guarantees of
complete event coverage. `biography_significance.py` keeps them explicit/testable.

- Newly required consequential factual anchors and indexed milestones trigger
  immediately. Travel, whereabouts, and masterwork-item entries accumulate as
  routine events instead; artifact creation is a milestone.
- Newly observed Death, UnexpectedDeath, or WitnessDeath thought content qualifies.
  An identical experience already present in the written timeline or remembered
  profile does not. Qualifying thoughts still do not establish a new death: the
  existing historian rules distinguish recalling/witnessing from occurrence.
- Personality changes qualify at 10 points from the written baseline; stress
  qualifies at a 10-band difference (10,000 raw units), without assigning a
  psychological diagnosis. Smaller changes accumulate against the same baseline.
- Minor additions require at least 8 occurrences, 3 distinct thought/event types,
  and 3 distinct observation times since the last successful biography. Reopening
  contributes nothing. Removed thoughts alone do not qualify. Many repetitions of
  just one routine type do not force another passage.
- Correcting known references, stable identity/relationships, or incompatible
  history still triggers revision rather than being hidden behind the filter.
  Additional unrelated resolved references alone do not force a new story.

The numeric thresholds are intentionally conservative starting values. Adjust
from playtest feedback, not from claims that every eight thoughts make a good story.

## Persistence and safety

Each unit has a separate `lorekeeper-views/<id>.biography-memory.json`, read only
by Python, containing the compact source payload, source-record checkpoint,
generation settings, continuation count, and a digest binding it to published
prose. Reads are capped at 1.2 MB. The GUI never reads this file. A failed model or
coverage check does not advance the checkpoint or replace the last good story.
Memory is written atomically before publishing the corresponding view; a crash
between writes produces a digest mismatch and conservative rebuild, not a duplicate
append. Records, game-time reversal, and latest-segment changes prevent cross-branch
continuations. This is not a claim of perfect save-lineage identification.

No remote conversation is resumed: the existing ephemeral Codex worker receives
explicit context per call. This follows the general stateless/context distinction
in [OpenAI's conversation-state guide](https://developers.openai.com/api/docs/guides/conversation-state).
Prior narrative is never promoted into the verified fact collection. Model and
reasoning settings are unchanged. Model prose still requires human review; factual
anchor checks do not prove every narrative connection is correct.
